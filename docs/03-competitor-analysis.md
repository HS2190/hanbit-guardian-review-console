## 2. 패턴 요약 (무엇을 하고 무엇이 비었나)

**공통으로 하는 것**
1. 변경은 앞으로의 건부터 — 명시: HackerOne 가이드·GitHub·Stripe·공공 경과조치(요약 확인) / 미언급: Bugcrowd·Radar / 위반 사례: HackerOne IBB·Uber(분쟁화).
2. 정책 객체는 새 버전 생성 + 구버전 archive(Stripe). 금액 제안은 표×등급 자동, 이탈은 사유 필수(Bugcrowd).
3. 중복은 "같은 조치로 해소되는가"로 판정하고 원본을 반드시 연결(Bugcrowd·HackerOne). 리테일은 거래 내 "같은 UPC 첫 1개"(SPAC) 또는 "방문당 1건"(이마트·롯데).
4. 한도는 개인 누적 금액·횟수를 깎는다(식약처·지자체·이마트). 버그바운티는 개인 한도 없이 프로그램 풀만. 확정 후 취소 불가(HackerOne·Bugcrowd).
5. 변경 전 확인은 "강제 적용과 평가를 분리하고, 결과를 만든 규칙을 보여준다"(IAM·Rulesets) — 단 둘의 평가 대상은 다르다(입력한 요청 맥락 vs 실제 활동).

**공통으로 비어 있는 것 (= 과제가 채울 자리) — 모두 "공개 문서에서 확인하지 못했다"는 뜻**
1. **정책 변경이 대기 건에 미치는 영향을 보여주는 화면** — 확인 못 함. GitHub는 공지문으로, HackerOne은 가이드 문장으로 대신한다.
2. **접수 당시 조건을 심사 화면에 고정 표시** — HackerOne calculator가 접수 시점 테이블을 자동 적용하는 동작은 공개 문서에서 확인 못 함.
3. **선순위 무효 시 차순위 처리** — 확인 못 함.
4. **개인 한도 × 중복 판정의 순서** — 개인 한도가 있는 공공/리테일 제도에서 중복 우선권 전이 규정을 확인 못 했고, 중복 규정이 정교한 버그바운티에는 개인 한도가 없다. 둘이 만나는 지점을 다룬 시스템을 확인 못 함.
5. **사건 단위 정의** — 리테일은 '방문'/'거래 내 UPC', 버그바운티는 '조치'. 마트 결함 제보에 '같은 원인·같은 시정 대상' 질문을 적용한 사례 확인 못 함.

## 3. 우리 과제로 옮길 때 주의

- IAM/Rulesets는 이미 접수된 건의 소급 영향을 보여주는 도구가 아니다. 그대로 옮기면 "대기 8건이 범위 밖이 됨"이라는 잘못된 메시지가 된다. 패턴(강제 전 결과 + 원인 규칙 표시)만 빌리고 대상은 "향후 접수분 / 기존 접수분 부담 유지"로.
- 이마트·롯데의 "방문당 1건"과 SPAC의 "거래 내 같은 UPC 첫 1개"는 모두 결함 경계의 근거가 아니다(각각 운영 편의 단위·거래 내 보상 단위). "동일 SKU ≠ 동일 결함"의 근거로 쓸 것은 Bugcrowd("같은 fix")·HackerOne("same root cause")의 좁은 명제뿐이며, 개별 상품/로트 경계는 대표 사례로 정해야 한다. SPAC을 부분 지급 근거로도 쓰지 않는다.
- Bugcrowd "중복자 포인트는 원본 승인 시 지급"은 포인트 지급 종속이지 판정 종속이 아니다. 우리의 "선행 판정 대기"는 "최초 유효자" 조건 충족 여부가 더 이른 후보의 유효성에 달려 있어서 생기는 우리의 설계다.
- 접수순 한도 배정은 공개 문서에서 확인하지 못했다. 가장 가까운 유사물(프로그램 풀)은 지급 시점 차감, 공공 개인 한도는 지급 순 누적으로 보임. 즉 지급(확정 이후) 시점 차감 유사 사례는 있으나 개인 한도 배정 *순서*는 확인하지 못했다 — 확정순은 운영 단순성을 비교할 설계 대안. 접수순은 "관행"이 아니라 "선택"으로 쓰고 논거(처리 순서 독립성)와 대가(같은 고객 선행 건 미판정 시 후속 건 확정 지연 — digest §3 R2′)를 명시.
- 권익위 기여도 배분은 과제의 "최초 유효자 1명 지급" 조건과 다른 모델이라 설계 범위 밖으로 한 줄만.
- 파인더갭 자체 제품의 정책·트리아지 UI는 공개 문서에서 확인하지 못했다. 결과물에서 파인더갭을 직접 언급하지 않는다(정본 §3 도메인 해독 서두 금지).
