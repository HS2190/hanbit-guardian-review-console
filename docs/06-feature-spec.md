## 1. 3축 상태 값 확정 (F1 — 과제가 "핵심"으로 지목)

세 축은 독립이다(PRD §4.6). 한 제보는 세 축의 값을 각각 하나씩 가진다. **어떤 축의 어떤 값에서도 `적용 버전`은 바뀌지 않는다** — 정책은 상태가 아니라 접수 시각의 함수다.

### 1.1 제보에 붙는 정책 필드 (상태 축이 아님, 불변)

| 필드 | 값 | 설정 시점 | 변경 |
|---|---|---|---|
| `received_at` | 서버 수신 시각(ms) | 자동 검증 통과 순간 | 불변 |
| `applied_version` | 그 시각의 발효 중 버전 ID (예: v1) | 자동 검증 통과 순간 | **불변. 어떤 화면에도 변경 컨트롤 없음**(P3·FR-07) |
| 표시 규칙 | 화면은 버전 번호보다 "`received_at` + 접수 당시 조건(결함 유형·기준액·한도·범위)"을 먼저 보인다. 버전 번호는 보조 | | |

동률·경계(PRD §4.2): 발효 시각 = 접수 시각이면 새 버전("이상"). 같은 ms면 제보 ID 오름차순 `[확인 필요]`.

|---|---|---|---|---|

| 재심 대상 | `rereview_pending` | 자동 또는 고객 이의로 진입, 미착수. **진입 사유**: `고객 이의` / `선행 건 번복`(하류 자동 진입, 대상 선행 건 ID) | 노출(보류) | 재심 착수 |
| 재심 중 | `in_rereview` | 재심 착수. 정책 고정, 사실 판단·중복 관계·산정만 수정 | 노출 | 재심 확정 · (선행 건 조정 중이면 시스템이 대기로 전이) |

- 2차 검수 지적 ②를 반영해 **재심 대상**(미착수)과 **재심 중**을 별도 값으로 둔다. 큐에서 "누가 봐야 하는 건"(재심 대상)과 "누가 보고 있는 건"(재심 중)이 구분돼야 K3 체류 측정과 착수 책임이 갈린다.
- 직권 재심(본사, 결정 ⑥)은 심사 완료 → 재심 중으로 직접 진입한다(사유 필수). 고객 이의·하류 자동 진입은 재심 대상을 거친다.
- "심사 중 ⇄ 보완 대기 / 선행 판정 대기"의 복귀는 항상 **심사 중**(또는 재심 중)으로 돌아온다. 자동 승인·자동 확정은 없다.

## 2. 전이표 (PRD §4.6·§5 → 트리거·조건·결과)

열 설명 — **트리거**: 누가·무엇으로. **선행 조건**: 시스템이 검사하는 것. **결과**: 세 축의 변화와 부수 효과. **정책과의 관계**: 그 전이에서 `applied_version`에 일어나는 일 — 모든 행이 "불변"이며 이것이 과제가 요구한 답이다. **화면**: 전이가 드러나는 곳(`screen-plan.md` 화면 ID).

### 2.1 접수 (트랙 A → 백오피스)

## 3. 정책 변경 × 상태 매트릭스 (F1·F3)

정책 변경 = 새 버전 **발행**(즉시 발효) 또는 예약 버전의 **발효 도래**. 셀은 "그 처리 상태의 제보에 무엇이 일어나는가". **거의 모든 셀이 "변화 없음"이고 그것이 답이다** — 정책 변경이 상태에 미치는 영향은 오직 하나, *발효 이후 새로 접수되는 제보의 적용 버전이 달라진다*(PRD §4.6).

## 5. 큐 보류 사유 목록 확정 (F4 · FR-09)

큐의 "보류 사유"는 별도 저장 필드가 아니라 3축 + 사유 필드에서 **파생**되는 표시 값이다. 카운터·필터·행 배지가 같은 목록을 쓴다.

## 6. "같은 결함 vs 다른 결함" 판단 가이드 + 고객 안내 장치 (H1 · Gemini 지적 ⑤)

### 6.1 심사자용 판단 가이드 (중복 비교 패널에 상시 노출)

판단 질문 하나: **"같은 원인이고, 같은 시정 대상인가?"** SKU 일치는 후보군 조건일 뿐 답이 아니다.

| 비교 축 (FR-12) | 같은 사건 신호 | 다른 사건 신호 | 사례 ② |
|---|---|---|---|
| 지점·이벤트 | 동일(후보군 전제) | — | 전부 성수점 |
| 상품 개체 (위치·사진) | 같은 진열대·같은 가격표·같은 개체 | 다른 개체(위치·순번·사진 각도로 식별) | #1110 "상단 3번째 개체" → 다른 개체 |
| 결함 유형 | 동일 유형 | 다른 유형이면 원인이 다름 | #1110 파손 vs #1103 가격표 → 별건 |
| 접수 시각 | 조치 기록 이전, 근접 | **지점 조치 완료 이후** 접수 = 재발 = 새 사건 | #1188 9/23 vs 조치 9/17 → 새 사건 |
| 증빙 | 같은 대상을 다른 각도로 | 다른 대상 | #1107 같은 가격표 → 중복 |
| 지점 조치 기록 | 조치 전 | 조치 완료 기록 존재 | #1103 "9/17 가격표 교체 완료" |

경계 규칙(확정):
- 개체 식별이 안 되면 → **사유 "개체 구분 불가"를 남기고 심사자가 판단**한다(자동 결정 없음). 기본값은 두지 않는다 — 두면 그 값이 곧 자동 확정이다.
- 같은 로트 다수 개체의 유통기한 경과 = 시정 대상 "로트 전량 철거" 하나 → **같은 사건**(PRD 가설 `[확인 필요]` 유지).
- "한 번의 매장 조치"를 확정 기준으로 쓰지 않는다 — 조치 기록은 재발 판단의 *경계 증거*이지 사건 수의 정의가 아니다.
- 판정 저장 시 **사유 템플릿**(선택 + 자유 서술): 같은 가격표 / 같은 개체 / 같은 로트 / 다른 개체 / 다른 결함 유형 / 조치 후 재발 / 개체 구분 불가.

### 6.2 고객 안내 UX 장치 (TA-2 데이터, 화면은 트랙 A)

- 중복 판정 안내에는 **원본의 접수 시각·ID·상태**(고객 정보 비노출)와 **사유 템플릿 값**("같은 가격표 하나가 원인")을 그대로 넣는다 — 심사자의 판단이 문장이 된다(FR-15).
- 새 사건 인정 + 부분 지급(#1188)은 두 문장으로 분리한다: "재발로 인정(9/17 조치 후 새 사건)" / "한도 50,000 중 30,000 기소비 → 20,000 지급". "새 사건 인정"과 "전액 지급"은 별개라는 것을 안내가 보여준다.
- 유효·0원(R3)은 "유효 — 한도 소진으로 지급 없음"으로 결과와 지급을 **다른 문장**으로 쓴다. 차순위 M에게는 "원본 접수 시각 10:00, 중복"만 — K의 한도 사정은 M에게 보이지 않는다.
- 이의 제기 기한(안내+14일)을 모든 안내에 붙인다.

- 동작: §3 집계 규칙으로 ① ② ③ 계산 + "현재 분류 유지 가정·중복·한도 미반영" 병기 + 변경 항목별 해당 건수·합계 + 방향 문장("이번 변경은 미확정 4건을 포함해 이미 접수된 7건의 적용 조건을 바꾸지 않습니다 — 미확정 유통기한 3건 90,000원은 줄지 않습니다" — 보증 범위는 접수 건 전부, 문장 형태는 UX 라이터 판단) + 향후 접수분 조건. 범위·한도 변경 시 해당 건수 + "접수 당시 범위·한도로 계속 심사(무효 아님)"
- 결과: 이 단계를 건너뛸 수 없음(발행 버튼이 여기에만 있음)
- 예외: 접수분 0건 → 세 값 0·0건 구조 유지, 향후 접수분 강조 / 집계 실패 → 발행 차단 + 재시도(집계 없이 발행 불가)
- 금지 문구: "대기 N건이 변경/무효된다", "최대 노출액", "예상 지급액", "예산에 영향 없음"
- 관련 컴포넌트: `ImpactPanel`, `AmountTriplet`
- Pain Point: 박 니즈 1 · Pain 1~4

#### F-POLICY-001-05. 발행(즉시)
