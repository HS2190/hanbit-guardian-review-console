# 부록 · 상태와 전이 전수

읽는 문서 [04 상태 모델과 정책 적용](../04-states.md)의 근거입니다. 세 축의 값 전부, 전이표, 정책 변경과 상태의 교차, 판정 순서, 큐의 보류 사유가 들어 있습니다.

## 1. 3축 상태 값 확정 (F1 — 과제가 "핵심"으로 지목)

세 축은 독립이다(PRD §4.6). 한 제보는 세 축의 값을 각각 하나씩 가진다. **어떤 축의 어떤 값에서도 `적용 버전`은 바뀌지 않는다** — 정책은 상태가 아니라 접수 시각의 함수다.

### 1.1 제보에 붙는 정책 필드 (상태 축이 아님, 불변)

| 필드 | 값 | 설정 시점 | 변경 |
|---|---|---|---|
| `received_at` | 서버 수신 시각(ms) | 자동 검증 통과 순간 | 불변 |
| `applied_version` | 그 시각의 발효 중 버전 ID (예: v1) | 자동 검증 통과 순간 | **불변. 어떤 화면에도 변경 컨트롤 없음**(P3·FR-07) |
| 표시 규칙 | 화면은 버전 번호보다 "`received_at` + 접수 당시 조건(결함 유형·기준액·한도·범위)"을 먼저 보인다. 버전 번호는 보조 | | |

동률·경계(PRD §4.2): 발효 시각 = 접수 시각이면 새 버전("이상"). 같은 ms면 제보 ID 오름차순 (가설).

### 1.2 처리 상태 축 (`processing_status`) — 9값 확정

| 값 | 코드 | 정의 | 큐 노출 | 이 상태에서 심사자가 할 수 있는 것 |
|---|---|---|---|---|
| 작성 중 | `drafting` | 고객 앱에서 작성 중. 적용 버전 미연결 | 비노출 | — |
| 제출 요청·검증 중 | `validating` | 제출 요청 후 자동 검증(§4.2: 이벤트 활성·기간, 필수 항목, 발효 중 버전의 범위 포함, 재제출 아님) 통과 전. 실패 시 작성 중으로 복귀(버전 차이면 TA-1 재확인). 통과 순간 = 접수 | 비노출(순간 상태) | — |
| 접수 | `received` | 정상 접수·적용 버전 고정. 심사 미착수·담당자 없음 | 노출 | 심사 착수 |
| 심사 중 | `in_review` | 담당자 착수·배정(동시성 잠금, NFR-03) | 노출 | 유효성 평가 · 결함 유형 재분류 · 중복 판정 · 보완 요청 · 무효 판정 · 확정 |
| 보완 대기 | `awaiting_evidence` | 보완 요청 발송 후 기한(요청+7일 고정) 또는 조기 완료까지. **하위 플래그**(단일 선택): `제출 없음` / `제출 있음·미검토` / `제출 검토됨·불충분` / `기한 경과·검토 필요` | 노출(보류) | 보완 확인(심사 재개) · 불충분 표시 · 만료 종결 |
| 선행 판정 대기 | `awaiting_precedent` | 시스템 전이. **사유 필드(복수 가능)**: `유효성` / `금액` / `선행 건 조정 중` + 각 사유의 대상 선행 건 ID(복수 가능) | 노출(보류) | 읽기 · 선행 건으로 이동. **판정 저장·확정 불가** |
| 재심 대상 | `rereview_pending` | 자동 또는 고객 이의로 진입, 미착수. **진입 사유**: `고객 이의` / `선행 건 번복`(하류 자동 진입, 대상 선행 건 ID) | 노출(보류) | 재심 착수 |
| 재심 중 | `in_rereview` | 재심 착수. 정책 고정, 사실 판단·중복 관계·산정만 수정 | 노출 | 재심 확정 · (선행 건 조정 중이면 시스템이 대기로 전이) |
| 심사 완료 | `completed` | 확정됨. 결과·지급 축 잠김 | 노출(완료 필터) | 재심 진입(직권) |

- 2차 검수 지적 ②를 반영해 **재심 대상**(미착수)과 **재심 중**을 별도 값으로 둔다. 큐에서 "누가 봐야 하는 건"(재심 대상)과 "누가 보고 있는 건"(재심 중)이 구분돼야 K3 체류 측정과 착수 책임이 갈린다.
- 직권 재심(본사, 결정 ⑥)은 심사 완료 → 재심 중으로 직접 진입한다(사유 필수). 고객 이의·하류 자동 진입은 재심 대상을 거친다.
- "심사 중 ⇄ 보완 대기 / 선행 판정 대기"의 복귀는 항상 **심사 중**(또는 재심 중)으로 돌아온다. 자동 승인·자동 확정은 없다.

|---|---|---|---|---|

| 반려 | `rejected` | 심사자 무효 판정 | 사유(허위·조작 / 이벤트 조건 외 / 기타 서술) | 미소비 |

**보조 필드 — 본건 유효성 평가(`validity_check`)**: `미평가` / `통과` / `미통과`. 결과 축이 아니다. 판정 순서 2단계(각자의 접수 정책으로 유효성 평가)의 산출물이며, 결과 축의 유효·최초 vs 중복은 3단계(최초 여부)에서 정해진다. 이 필드가 있어야 "유효성은 통과했으나 선행 건 때문에 최초 여부 미확정"(선행 판정 대기-유효성)을 결과 축 "—"와 함께 표현할 수 있다.

## 2. 전이표 (PRD §4.6·§5 → 트리거·조건·결과)

열 설명 — **트리거**: 누가·무엇으로. **선행 조건**: 시스템이 검사하는 것. **결과**: 세 축의 변화와 부수 효과. **정책과의 관계**: 그 전이에서 `applied_version`에 일어나는 일 — 모든 행이 "불변"이며 이것이 과제가 요구한 답이다. **화면**: 전이가 드러나는 곳(`screen-plan.md` 화면 ID).

### 2.6 정책 버전 전이표 (P1 · 결정 ⑨ — 정책 현황 배지의 근거, 3차 검수 E)

버전 상태 4값: `초안(draft)` / `발행됨·발효 전(scheduled)` / `발효 중(effective)` / `이전(superseded)`. 한 이벤트에 초안 ≤ 1 · 발행됨·발효 전 ≤ 1 · 발효 중 = 1(접수 개시 후). 초안은 수정 가능한 작업본이고, 발행 이후 어떤 상태의 버전도 편집 경로가 없다(FR-02).

## 3. 정책 변경 × 상태 매트릭스 (F1·F3)

정책 변경 = 새 버전 **발행**(즉시 발효) 또는 예약 버전의 **발효 도래**. 셀은 "그 처리 상태의 제보에 무엇이 일어나는가". **거의 모든 셀이 "변화 없음"이고 그것이 답이다** — 정책 변경이 상태에 미치는 영향은 오직 하나, *발효 이후 새로 접수되는 제보의 적용 버전이 달라진다*(PRD §4.6).

| 처리 상태 ＼ 변경 | 금액 하향 (예: 유통기한 30,000→10,000) | 금액 상향 | 범위 축소 (카테고리·인정 유형 제외) | 범위 확대 | 한도 하향 (50,000→20,000) | 한도 상향 | 발행됐지만 **발효 전**(예약) |
|---|---|---|---|---|---|---|---|
| 작성 중 | 제출 시 **새 버전 적용**. 동의 버전과 다르면 TA-1 재확인(변경 항목만) | 동일 | 제출 시 자동 검증에서 해당 카테고리·유형 **정상 접수 안 됨** → 작성 중 복귀·범위 제외 안내 | 제출 시 새 버전 적용(신규 허용 항목 접수 가능) | 제출 시 새 버전 한도 적용. 같은 고객 기존 소비와 결합해 0원 가능(R1·결정 ①) | 동일 방식 | **영향 없음** — 발효 전 버전은 현재 정책이 아님(§4.1). 발효 도래 후 이 행의 규칙 |
| 제출 요청·검증 중 | 동의 버전 ≠ 수신 시각 발효 버전이면 접수 안 하고 재확인(T02-F2) | 동일 | 동일 + 범위 검증 실패 시 T02-F1 | 동일 | 동일 | 동일 | 영향 없음 |
| 접수 | **변화 없음**. 적용 v1 유지. 큐에 "적용 v1 ≠ 발효 중 v2" 표시만 추가 | 변화 없음(상향 소급 없음 — §11 대안 2 기각) | **변화 없음, 무효 아님** — v1 범위로 계속 심사 | 변화 없음 | 변화 없음 — v1 한도로 계산 | 변화 없음 | 영향 없음 |
| 심사 중 | 변화 없음. 상세의 "현재" 열이 v2로 바뀜(비교용) | 변화 없음 | 변화 없음, 무효 아님 | 변화 없음 | 변화 없음 | 변화 없음 | 영향 없음 |
| 보완 대기 | 변화 없음. **보완은 원정책 유지**(결정 ④) | 변화 없음 | 변화 없음 — 보완이 상품·결함을 바꾸면 새 제보(그 시점 = v2 범위 검증) | 변화 없음 | 변화 없음 | 변화 없음 | 영향 없음 |
| 선행 판정 대기 | 변화 없음. 산정 범위(하한~상한)도 불변(선행 건·본건 모두 각자 접수 버전) | 변화 없음 | 변화 없음 | 변화 없음 | 변화 없음 | 변화 없음 | 영향 없음 |

집계 규칙(FR-04) — 세 값은 **지급 축 값만으로** 가른다(처리 축 무관. 3차 검수 C: 처리 축 정의는 재심 대상·재심 중 건의 확정액을 ①②와 이중 집계했음):
- ① 지급 완료 = 지급 축 ∈ {완료, 조정 중} (조정 중은 괄호 병기 (가설) P5)
- ② 지급 확정·미송금 = 지급 축 ∈ {지급 확정, 지급 중, 실패} (실패 = 확정액이 살아있고 미송금 (가설) P5)
- **③ 미확정 기준액 합계 = 지급 축 ∈ {미정, 확정 대기}인 건의 현재 분류 기준 기준액 합**(중복·개인 한도 미반영 · 현재 분류 유지 가정)
- 지급 해당 없음 건은 어디에도 들지 않는다. **①·②·③은 지급 축 값이 겹치지 않으므로 서로 배타적**이다 — 재심 대상·재심 중 건도 확정액이 살아있으면 ① 또는 ②에, 확정 전이면 ③에 정확히 한 번 들어간다.
- 검산(사례 ① 9/15 10:23): ① #1003 30,000 + #1015 30,000 = **60,000(2건)** / ② #1028 30,000 = **30,000(1건)** / ③ #1031 30,000 + #1036 15,000 + #1039 30,000 + #1042 30,000 = **105,000(4건, 전부 지급 미정)** → 그중 유통기한 경과 #1031·#1039·#1042 = **90,000(3건)**. PRD §6 사례 ① 수치와 일치.

## 4. 판정 순서(PRD §4.5) → 심사자 행동 시퀀스 (F5·F6·F7)

화면(심사 상세)이 이 순서를 강제하지 않는다(GPT 지적: 판정 순서 = 화면 순서 완화). 대신 **저장 가능한 행동의 선행 조건**으로 강제한다.

| 단계 | 시스템이 먼저 하는 일 | 심사자 행동 | 저장 조건 | 산출 |
|---|---|---|---|---|
| 0 근거 | `received_at`·`applied_version`으로 접수 당시 조건을 표시. 발효 중 버전과 차이 나는 항목 표시 | **읽기만** (선택 컨트롤 없음) | — | — |
| 1 후보군 | 같은 지점·이벤트에서 SKU/위치/결함 유형/시각(±7일 (가설) P3)이 겹치는 건 자동 구성. **예외(P3)**: 같은 SKU + 같은 결함 유형 + 지점 조치 기록이 있는 건은 시각 창과 무관하게 후보 포함 — 재발 판단의 경계 증거(#1188 vs #1103은 6일 21시간으로 창 경계에 걸림). **자동 중복 확정 없음** | 후보 요약 확인 → 필요 시 비교 패널 열기 | — | 후보 목록(각 후보의 처리·결과·접수 시각) |
| 2 유효성 | 증빙·결함 유형·범위를 **본건의 접수 정책**으로 대조 | 증빙 열람 → (재분류 + 사유) → 유효성 평가 `통과` / `미통과` / 보완 요청 | 재분류는 사유 필수. 보완 요청은 1회 | `validity_check`. 미통과면 결과 범위 외/반려(T12) |
| 3 최초 | 후보군 중 본건보다 이른 건의 결과를 검사 → 미판정이면 **선행 판정 대기(유효성)**(T15-a) | 이른 유효 건이 있으면 **중복(원본 지정) 또는 별건(사유)** 판정 | 중복은 원본 필수 | 결과 유효·최초 또는 중복 |
| 4 한도 | 같은 고객·이벤트 누적 소비를 접수순으로 계산. 이른 건 미판정이면 **선행 판정 대기(금액)**(T15-b) + 범위 표시 | 산식 확인(수정 불가) → 「지급 확정」 | 대기 사유 없음 · 본인 담당 | 최종액(0원 포함) 잠금 |
| 5 안내 | 판정 데이터로 안내 근거 자동 구성 | 미리보기 확인(편집 불가, 사유 텍스트만 심사자 입력분) | — | TA-2 데이터 |

심사자가 손댈 수 있는 것은 §4.3의 ①②③④뿐이다. **금액 입력 필드·정책 버전 선택 컨트롤은 어떤 상태에도 존재하지 않는다**(FR-07·08).
