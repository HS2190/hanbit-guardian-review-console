## 0. 단일 원칙

> **기존 제보에는 접수 당시 정책을 적용한다. 새 정책은 발효 이후 정상 접수된 제보부터 적용한다. 심사자는 적용 정책을 선택할 수 없다.**

파생 규칙 4개(P1 정책 버전 불변 · P2 접수 시점 연결 · P3 심사자 선택 불가 · P4 영향 확인의 방향)는 §4가 정본이다.

외부 근거의 범위(digest §2): "접수 당시 정책 적용"은 HackerOne 운영 가이드(*"always honor the commitments published at the time of the report"*)·GitHub 2026-07 하향 개편의 백로그 grandfathering·Stripe의 새 Price 발행 모델이 공유하는 **명문 관행**이다(플랫폼 권고·단일 공지·결제 객체 모델 — "업계 표준"으로 일반화하지 않는다). 그 위의 "접수 순간 자동 고정"과 "심사자 선택 불가"는 관행보다 강한 **우리의 설계 선택**이다(HackerOne·Bugcrowd는 사유 조건부 커스텀 금액을 허용한다). 선택 이유는 §4.3.

## 1. 배경 및 문제 정의

### 1.1 상황과 트랙 선택

한빛마트는 고객이 매장 결함(유통기한 경과·가격표 오류·파손/오염·통로 적재물·POP 오정보)을 앱으로 제보하면 본사 심사를 거쳐 리워드를 지급하는 '매장 지킴이 리워드 이벤트'를 지점 단위로 운영한다. 지점은 이벤트 운영 중에도 결함 유형별 금액·대상 범위·1인 한도를 수시로 바꿀 수 있고, 같은 결함은 최초 유효 제보자 1명에게만 100% 지급한다. 제출부터 지급까지 수일~수주가 걸린다.

정책을 *바꾸는* 쪽(지점)과 *적용하는* 쪽(본사)의 판단이 분리돼 있고, 한쪽의 변경이 다른 쪽의 심사 오류로 이어진다. 둘은 서로의 화면을 보지 않는다. 그 접합부를 통제하는 화면이 트랙 B다. 트랙 A의 "납득"은 트랙 B가 만든 근거 데이터가 있어야 성립하므로, B를 깊이 설계하고 A는 그 데이터를 소비하는 접점으로 정의한다.

### 1.2 문제 정의 — 기준과 수단의 불일치

> **정책이 변경될 때 기존 제보에 무엇을 적용할지에 대한 *기준*과, 심사자가 그 기준을 *확인·집행하는 수단*이 일치하지 않는다.**

과제 원문의 세 증상(공정성 분쟁·소급 적용/기준 혼선·범위 변경 무효)은 하나의 원인에서 나온다. 기준이 없거나(지점은 "낮추면 다 낮아진다", "범위에서 빼면 기존 건도 무효"라고 생각), 기준이 있어도 심사 화면에서 접수 당시 조건을 찾을 수 없어 현재 정책을 적용한다. 데이터 이력이 있어도 화면에서 못 찾으면 같은 문제가 난다 — 그래서 데이터 구조만의 결함으로 단정하지 않는다.

**왜 문제인가 (근거·유추 한계 병기)**
- 실사례: HackerOne IBB 2026-05 하향(연구자 주장: 75~89% 하향이 *"long after the work was already done"* 적용됨 / 플랫폼 인정 사실: 스폰서 기여금에 따라 바운티가 자동 조정됨)과 Uber 2016 범위 축소 분쟁의 공통 언어는 금액이 아니라 **"이미 한 일에 대한 사후 변경 + 미통지"**다(digest E5·synthesis I2). 과제의 "지점 예산 압박 → 하향"과 가장 가까운 실사례이며, 언론 보도 1건·소급 여부에 대한 플랫폼 직접 답변은 없다.
- 공정성 인식: 제출 시점에 본 리워드를 기준 거래로 인식하므로 사후 하향은 "얻지 못한 이득"보다 "약속의 삭감"으로 읽혀 심리적 손실로 크게 작용한다(KKT 1986 — 응답자 비율, 2차 출처, 임금·보너스 맥락 → 제보 리워드 적용은 유추).

## 4. 규칙 정본 (원칙에서 파생되는 규칙)

### 4.1 P1 정책 버전 불변 — 발행과 발효의 구분
- 정책 = 이벤트별 규칙 묶음(결함 유형별 금액 / 대상 카테고리 / 인정 결함 유형 / 1인 최대 지급 한도). 버전 상태: **초안 → 발행됨(발효 전) → 발효 중 → 이전**. 초안만 수정 가능. 발행하면 그 버전은 불변이며 새 버전 번호를 갖는다.
- **발행(publish)** = 버전을 확정·불변화하는 행위. **발효(effective)** = 그 버전이 접수 건에 적용되기 시작하는 시각. 즉시 발행은 발행 시각 = 발효 시각. 예약 발행(결정 ⑨)은 둘이 다르며, **발행됐지만 발효 전인 버전은 "현재 정책"이 아니다** — 큐·상세의 비교 대상, 접수 시 적용 버전, TA-1 재확인 기준은 모두 *발효 중 버전*이다.
- 한 시점에 발효 중 버전은 항상 1개. 이벤트는 발효 중 버전이 있어야 접수를 개시할 수 있다.

### 4.2 P2 접수 시점 연결
- 흐름: **제출 요청 → 자동 검증 → 정상 접수·정책 연결**. 자동 검증 = 이벤트 활성·기간 내, 필수 항목(지점·결함 유형·사진 1장 이상), 제출 시점 발효 중 버전의 대상 카테고리·인정 결함 유형 포함, 동일 고객의 동일 제보 재제출 아님. 통과해 서버가 수신한 시각이 **접수 시각**이고, 그 시각의 발효 중 버전이 **적용 버전**이다. 작성 중·제출 요청·검증 중은 아직 연결 전이며, 정상 접수 이후에는 어떤 발행도 적용 버전을 바꾸지 않는다.
- 적용 버전은 **고객이 마지막으로 동의한 버전**과 같아야 한다(TA-1). 동의와 서버 수신 사이에 다른 버전이 발효되면 접수하지 않고 재확인한다.
- 동률: 접수 시각은 밀리초, 같으면 제보 ID 오름차순 `[확인 필요]`. 발효 시각 = 접수 시각이면 새 버전 적용("이후"가 아니라 "이상"). 화면에서는 버전 번호보다 "접수 시각 + 접수 당시 조건"이 먼저 식별돼야 한다 — 버전 참조 하나면 충분하고 "스냅샷 시스템"으로 과장하지 않는다.

### 4.3 P3 심사자 선택 불가 — 그러나 사실 판단은 가능
- 심사자는 적용 버전을 바꿀 수 없고 금액을 직접 입력할 수 없다.
- 심사자가 할 수 있는 것: ① 결함 유형 재분류 ② 중복 관계 판정(원본 지정·해제) ③ 유효/무효 판정 ④ 보완 요청. ①②를 바꾸면 사유를 필수로 남기고, 금액은 **접수 정책 테이블**에서 자동 재계산된다(Bugcrowd "기준 이탈 시 사유 강제"의 변형, synthesis I8). 재분류된 유형이 접수 정책의 인정 유형 밖이면 결과는 "범위 외"다 — 현재 정책에 있어도 적용하지 않는다.
- 왜 관행보다 강하게 잡는가: 과제의 심사 오류는 *선택지가 있어서* 생긴다. 접수 시각이 정해지면 적용 버전은 계산 결과이지 판단이 아니다. 판단이 필요한 곳(사실)과 필요 없는 곳(정책)을 나누면 실수 표면이 줄고, 재량이 필요한 예외는 사유 기록으로 감사 가능해진다.

### 4.4 P4 영향 확인의 방향
- 발행 직전 영향 확인의 메시지는 **"정책을 낮춰도 이미 접수된 제보의 부담은 줄지 않는다"**다 — 기존 약속과 향후 변경의 *경계*를 보여준다.
- 기존 접수분 금액은 세 값으로 분리한다. ① 지급 완료 ② 지급 확정·미송금 ③ **미확정 기준액 합계** = "현재 분류 기준의 미확정 제보 기준액 합계, 중복·개인 한도 미반영". ③을 "예상 지급액"·"최대 노출액"으로 부르지 않는다. 결함 유형 재분류가 일어나면 합계가 바뀌므로 **"현재 분류 유지 가정"**을 병기한다(사례 ①: 105,000 → 파손 1건이 유통기한으로 재분류되면 120,000).
- 변경 항목이 **금액**이면 해당 유형의 미확정 건수·합계를, **범위(카테고리·결함 유형)·한도**이면 미확정 건 중 해당 건수를 보여주고 "접수 당시 범위·한도로 계속 심사(무효 아님)"를 명시한다. 향후 접수분에는 새 조건이 적용된다.

### 4.5 판정 순서 (중복 → 한도) — 설계 가정으로 선언
1. **동일 결함 후보군** 구성: 같은 지점·같은 이벤트에서 SKU/위치/결함 유형/시각이 겹치는 제보. SKU 일치만으로 중복을 자동 확정하지 않는다.
2. 각 제보를 **각자의 접수 정책**으로 유효성 평가한다(범위·인정 유형·증빙).
3. 유효한 후보 중 접수 시각이 가장 이른 것이 **최초 유효자**. 더 이른 후보가 미판정(심사 중·보완 대기)이면 확정을 보류한다 → "선행 판정 대기(유효성)". 이 대기는 최초 유효자 조건에서 오며 한도 배정 방식과 무관하다(digest R2).
4. 최초 유효자의 **개인 한도**를 계산해 지급액을 확정한다. 한도 단위 = 고객 × 이벤트, 버전이 바뀌어도 누적은 초기화하지 않으며, 각 제보는 자기 접수 버전의 한도값으로 계산한다. 중복·무효·범위 외는 한도를 소비하지 않는다.
   - 배정은 **접수순**: 같은 고객의 더 이른 제보가 미판정이면 후속 건의 금액을 잠글 수 없다 → "선행 판정 대기(금액)"(digest R2′). 확정 시 금액과 한도 소비가 잠긴다.
   - 유효하지만 잔여 한도 0원은 **반려가 아니다**(유효성 ≠ 지급 가능성). 부분 지급(잔여 20,000 → 20,000)을 허용한다. "100%"는 중복자끼리 분할하지 않는다는 뜻이다.

1~3의 "같은 조치로 해소되는가"와 원본 링크 필수는 Bugcrowd·HackerOne 관행, 4의 접수순 배정과 지위 불이전은 외부 근거 없는 설계 선택이다(digest §2). 논거는 §11.

### 4.6 상태 모델 — 3축 (기획자가 확정, PRD는 축과 전이 규칙만)

| 축 | 값 |
|---|---|
| 처리 상태 | 작성 중 → 제출 요청 → 자동 검증 → 접수 → 심사 중 ⇄ 보완 대기 / 선행 판정 대기 → 심사 완료 → (재심) |
| 심사 결과 | — (미정) / 유효·최초 / 중복 / 범위 외 / 증빙 불충분 / 반려 |
| 지급 상태 | 미정 / 확정 대기 / 지급 확정 / 지급 중 / 완료 / 실패 / 조정 중 / 해당 없음 |

전이 규칙(정책과의 관계 — 과제가 "핵심"으로 지목한 것):
- **어떤 상태에서도 적용 정책은 바뀌지 않는다.** 정책 변경이 상태에 미치는 영향은 오직 하나 — 발효 이후 *새로* 접수되는 제보의 적용 버전이 달라진다.
- **세 축은 독립이다.** 심사 결과는 유효성이 정해지는 시점에 채워지며 처리 상태 "완료"를 기다리지 않는다(사례 ③ #1063: 처리 *선행 판정 대기* / 결과 *유효·최초* / 지급 *확정 대기*). **확정 대기** = 결과가 유효이나 지급 확정(금액·한도 잠금) 전. **지급 확정** = 잠금 후 송금 전. **해당 없음** = 중복·범위 외·증빙 불충분·반려·유효 0원.
- 보완 대기·만료·상품/결함 변경은 결정 ④, 재심과 하류 재심 대상은 결정 ③·⑥, 지급 후 번복과 한도 복원은 결정 ⑤를 따른다.
- 이벤트 종료 후에도 접수된 건은 접수 정책으로 끝까지 심사한다. 종료는 신규 접수만 막는다.

| ⑨ | 발효 예약 | **즉시 발행(발행 = 발효) 기본, 예약은 Should.** 이벤트당 1건, 발효 전 취소 가능, 예약 중 즉시 발행하면 대체 여부 확인. 발행됐지만 발효 전 버전은 현재 정책이 아니다(§4.1) | 공정성 문제는 즉시 발효 + 접수 시 고정으로 해결된다. 예약은 안내물 교체·공지 시점을 맞추는 운영 편의로 근거가 추정 → Should. 예약을 핵심 해법으로 두면 취소·대체·중첩 설명이 늘고 원칙이 흐려진다 | 예약 필수 / 예약 없음 |
| ⑩ | 정책 변경 시 통지 | **심사자**: 큐·상세에서 "적용 버전 ≠ 발효 중 버전"을 식별할 수 있어야 한다(Must — 오적용 방지). **고객(§10)**: TA-1 마지막 동의 버전 = 접수 적용 버전 보장(Must), TA-2 안내 근거 데이터(Must), TA-3 changelog 탐색(Should — 단 변경 항목 데이터는 TA-1·영향 확인이 쓰므로 Must) | 분쟁 실사례의 공통 원인은 "미통지"(synthesis I2). 심사자 통지는 K1에 직결. changelog 탐색의 도메인 효과는 추정 → Should | 실시간 푸시(범위 밖, 트랙 A 화면) |

등급의 근거는 네 갈래다. **① 과제의 명시적 제약** — 정책 수시 변경·최초 유효자 1명·개인 한도·트랙 선택·상태 흐름과 정책 적용의 관계(과제 정본 §2). **② 선택한 해법(단일 원칙)을 완결하는 데 필수** — 버전 불변·접수 정책 연결·영향 확인·중복 비교·한도 산정·예외 전이. 하나라도 빠지면 원칙이 성립하지 않는다. **③ 제출 전략·사용자 승인 범위** — Figma 정본·신규 DS·토큰·베리언트(과제 정본 §0), JD 주요 업무(데이터 집약 화면 위계·Figma DS)도 여기. **④ 운영 편의 확장** — 추정 근거이므로 Should/Nice에 검증 조건을 붙인다. "외부 지정 스펙은 Must 고정" 원칙은 ①·③에만 적용하고, 과제의 "화면 예시"는 범위 참고이지 강제 화면이 아니다.

## 9. 요구사항

### 9.1 문제 → 지표 → 유저 스토리 → 요구사항 추적

| 문제 | 지표 | 유저 스토리 | FR |
|---|---|---|---|
| 지점이 낮추면 기존 부담도 준다고 오해 / 범위 축소 = 무효로 오해 → 예산 초과·분쟁 | K2·K4 | 박지훈: 발행 전에 기존 접수분과 향후 접수분의 경계를 보고 발행하고 싶다 | FR-01~05 |
| 심사자가 접수 당시 정책을 못 찾아 현재 정책 적용 | K1·K5 | 최민아: 상세 진입 즉시 접수 당시 조건을 보고, 정책을 고를 수 없어야 안심한다 | FR-06~10 |
| SKU만 보고 중복 / 선순위 미확정인데 후속 확정 | K3·K5 | 최민아: 후보를 원인·시정 대상으로 비교하고 원본 상태를 보며 판정하고 싶다 | FR-11~15 |

### 9.2 기능 요구사항 (FR) — 수용 기준은 검증 행동과 예상 결과

**정책 (F2·F3·F9·F10)**
- FR-01 지점 담당자는 자기 지점 이벤트의 정책 초안을 만들고 수정할 수 있어야 하며, 발행된 버전은 어떤 필드도 수정할 수 없어야 한다. *수용*: 발행 버전에 수정 시도 시 저장 경로가 없고, 변경은 초안 생성으로만 가능.
- FR-02 발행 시 새 버전 번호·발행 시각·발효 시각·발행자가 기록되고, 이전 버전은 접수 건이 참조할 수 있어야 한다. 발행됐지만 발효 전인 버전은 "현재 정책"으로 표시·적용되지 않아야 한다. *수용*: v2 발행 후 v1 참조 제보의 적용 조건이 v1 값 그대로 조회됨. 예약 버전이 있는 동안 큐·상세의 비교 대상은 발효 중 버전.
- FR-03 발행 직전 영향 확인을 건너뛸 수 없어야 하며, 기존값과 변경값을 항목별로 비교할 수 있어야 한다. *수용*: 변경된 항목만 강조되고, **동일 값 발행은 막히며 사유("변경된 항목 없음")가 표시**된다.
- FR-04 영향 확인은 §4.4의 세 값과 "현재 분류 유지 가정"을 보여야 하며, 변경 항목이 범위·한도일 때 미확정 건 중 해당 건수와 "접수 당시 범위·한도로 계속 심사(무효 아님)"를 명시해야 한다. *수용*: 사례 ①에서 60,000(2건) / 30,000(1건) / 105,000(4건, 그중 변경 항목 해당 3건 90,000)이 표시되고 "대기 N건이 변경된다/무효가 된다"류 문구가 없다. 범위 축소 변형에서 "신선식품 3건 계속 심사(무효 아님)"가 표시된다.
- FR-05 발효 예약(Should)은 결정 ⑨를 따른다. *수용*: 두 번째 예약 시도 시 첫 예약 대체 확인 없이 저장되지 않음.

**심사 상세·큐 (F4·F5)**
- FR-06 심사 상세 진입 시 접수 시각과 접수 당시 조건(결함 유형·기준액·한도·범위)을 즉시 식별할 수 있어야 하며, 버전 번호는 보조 정보다. *수용*: 사례 ① #1042에서 "9/15 09:47 · 유통기한 경과 30,000원"이 추가 조작 없이 식별됨.
- FR-07 적용 정책과 발효 중 정책이 다르면 그 차이를 식별할 수 있어야 하되, 적용 정책은 읽기 전용이고 선택·변경 경로가 없어야 한다. *수용*: 상세·큐 어디에도 적용 버전을 바꾸는 컨트롤이 없음(K1).
- FR-08 심사자는 결함 유형 재분류·중복 관계 변경·유효/무효 판정을 할 수 있어야 하고, 재분류·관계 변경 시 사유 없이는 저장되지 않아야 한다. 금액은 접수 정책 테이블에서 자동 재계산되며 직접 입력할 수 없다. *수용*: 재분류 후 기준액이 접수 정책의 해당 유형 값으로 바뀌고 사유가 기록됨. 인정 유형 밖으로 재분류하면 결과 "범위 외".
- FR-09 큐에서 각 건의 처리 상태·보류 사유(보완 대기 / 선행 판정 대기-유효성 / 선행 판정 대기-금액 / 조정 중)·적용 버전≠발효 중 버전 여부를 식별할 수 있어야 하며, 사유별 건수를 상세 진입 없이 확인할 수 있어야 한다.
- FR-10 확정이 막힌 경우 이유와 다음 행동(대상 선행 건으로 이동)이 표시되어야 하며, 이유 없는 비활성 상태만 두지 않는다. 사유가 복수면 모두 표시한다. *수용*: 사례 ③ #1063에서 "같은 고객의 선행 건 #1042 판정 필요"와 이동 경로가 표시.

**중복 판정 (F6)**
- FR-11 같은 지점·이벤트에서 SKU/위치/결함 유형/시각이 겹치는 제보를 후보군으로 볼 수 있어야 하며, SKU 일치만으로 중복이 자동 확정되지 않아야 한다. *수용*: 사례 ② #1110은 후보군에 나타나되 기본값이 "중복"이 아님.
- FR-12 후보 비교는 지점·상품 개체(위치·사진)·결함 유형·접수 시각·증빙·지점 조치 기록을 축으로 대조할 수 있어야 한다. *수용*: 사례 ② 4건에 대해 판정 근거가 축별로 대조 가능하고, #1188 비교에 #1103의 9/17 조치 기록이 보임.
- FR-13 중복 판정 시 원본 지정이 필수이며, 원본의 ID·처리 상태·심사 결과·접수 시각이 표시되어야 한다(원본 고객 개인정보 비노출). *수용*: 원본 없이 "중복" 저장 불가.
- FR-14 후보군에 더 이른 미판정 건이 있으면 최초 유효 확정이 보류되고 "선행 판정 대기(유효성)"로 전환되어야 한다. 선행 건이 무효·만료되면 자동 재검토(심사 중으로 복귀)되며 자동 승인되지 않는다. *수용*: 선행 건 만료 시 후속 건이 "심사 중"으로 돌아오고 결과는 비어 있음.
- FR-15 중복 판정 사유·비교 근거는 고객 안내 근거(TA-2)로 재사용 가능한 형태로 저장되어야 한다. *수용*: #1107 안내 근거에 원본 #1103 접수 시각 9/16 14:02와 사유 "같은 가격표"가 포함.

**지급 확정 (F7·F8)**
- FR-16 지급액 산식은 기준액(접수 정책) → 개인 한도 조정(접수 정책의 한도 − 이벤트 누적 소비) → 최종액 순서로 표시되어야 한다. *수용*: 사례 ③ 분기 A에서 30,000 → −10,000(잔여 20,000) → 20,000. 사례 ② #1188에서 30,000 → 잔여 20,000 → 20,000.
- FR-17 잔여 한도가 음수면 0으로 절삭하고 환수하지 않는다. 유효·0원은 심사 결과 "유효"를 유지하고 지급 상태만 "해당 없음(한도 소진)"이어야 한다. *수용*: R1 케이스에서 B = 0원, 결과 "유효·최초".
- FR-18 같은 고객의 더 이른 제보가 미판정이면 후속 건은 "선행 판정 대기(금액)"로 전환되고 금액 범위(하한~상한)를 보여야 한다. *수용*: 사례 ③ #1063에 "20,000~30,000".
- FR-19 확정 시 금액과 한도 소비가 잠기며, 이후 정책 변경·타 건 판정으로 자동 재계산되지 않아야 한다. *수용*: 확정 후 같은 고객의 다른 건 판정이 바뀌어도 확정액 불변(재심 경로로만 변경).
- FR-20 보완 요청·기한·만료·상품/결함 변경 시 원 건 처리는 결정 ④를 따른다. *수용*: 2회째 보완 요청 컨트롤 없음(§14-5 시스템 귀책 재요청 예외 제외), 만료 시각 = 최초 요청 시각 + 7일이며 추가 제출 후에도 불변, 기한 내 추가 제출 경로 존재, 만료 시 이 건을 선행으로 둔 대기 건이 재검토로 전환(사례 ③ 대안 분기 B: #1042 만료 → #1063 재검토). 기한 전(9/24) 제출 → 기한 후(9/26) 검토 → 충분하면 기존 순위·v1로 심사 계속(자동 종결 없음).

### 9.3 비기능 요구사항 (NFR)
- NFR-01 모든 판정·수정·발행은 행위자·시각·이전값·이후값·사유가 기록되어야 한다(탐색 UI는 범위 밖).
- NFR-02 권한: 지점 담당자는 자기 지점 정책만 편집·발행하고 제보는 읽기 전용, 타 지점에 접근할 수 없다. 본사 심사자는 전 지점 제보를 심사·확정하고 정책은 읽기 전용이다. 조정(환수·추가 지급·한도 복원)은 본사 운영팀 별도 권한 `[확인 필요]`.
- NFR-03 동시성: 같은 초안을 두 사람이 편집하면 나중 저장이 이전 저장을 덮어쓰지 않고 충돌을 알려야 한다. 같은 제보를 두 심사자가 열면 확정은 한 명만 가능해야 한다.
- NFR-04 접근성: 3축 상태는 색만으로 구분하지 않고 라벨·아이콘을 병기하며, 텍스트 대비는 WCAG AA(4.5:1) 이상. 발행·확정 등 비가역 행동은 키보드로 조작 가능해야 한다.
- NFR-05 지정 viewport(1440×900)에서 심사 상세의 접수 근거·산정 상태·차단 이유의 **요약**을 스크롤 없이 확인할 수 있어야 한다. 상세는 스크롤을 허용한다(가설 — 기획자가 검증).

## 11. 검토했다가 버린 대안 3 (과제 필수 답변 3 — 대표 사례에 대입해 비교. 기각 논거는 "채택 사례 없음"이 아니라 실질 논거)

| 대안 | 대입 사례 | 결과 | 트레이드오프 | 기각 이유 |
|---|---|---|---|---|
| **1. 이벤트 중 정책 변경 금지** | 사례 ①: 박지훈은 v2를 발행할 수 없다 | 9/15 이후 접수분도 30,000. 예산 소진 시 선택지는 이벤트 조기 종료뿐 → 대기 건은 그대로 두고 신규 접수만 막힌다. 고객은 "갑자기 끝났다"를 경험 | 일관성 ↑ vs 유연성 ↓ | 예산 압박이 변경 동기라는 것이 과제의 전제다. 변경을 막으면 문제를 회피하는 것이고, 결과는 종료라는 더 큰 변경이다. 채택안은 신규 접수에 변경을 허용하고 기존 접수 조건을 보존해 두 요구를 모두 충족한다 |
| **2. 미완료 제보 전체에 유리한 조건 소급** | 사례 ①의 반대 방향: v2가 유통기한 경과 30,000 → 40,000 상향 + 한도 50,000 → 30,000 하향이라면 | 상향 대상은 미확정 유통기한 3건 → 기준액 증가분 30,000(실제 부담은 유효성·중복·한도에 따라 다름 — 예산 사정을 무시). 김서연에게 40,000은 유리하지만 한도 30,000은 불리 — 두 건 가진 고객에겐 합계가 줄어 "유리함"을 판정할 주체·기준이 없다. 상향을 소급하면 지점은 상향 자체를 꺼리게 된다 | 참여자 혜택 ↑ vs 예산·규칙 복잡성 ↑ | '유리함'은 항목 단위로 판정 불가(금액↑·한도↓ 복합), 선택 주체 부재로 새 분쟁, 지점 예산과 충돌. 추가 보상은 별도 조치이며 범위 밖. **선택적 소급(심사자·지점 재량)도 같은 이유로 채택하지 않는다** |
| **3. 개인 한도 확정순 배정** | 사례 ③ + R1 | 사례 ③: #1063을 9/18에 30,000 잠금 → #1042 유효 시 20,000. 총액 같음(50,000), 배분이 처리 순서로 결정. R1(한도 하향): 담당자가 A→B 처리하면 합 30,000, B→A면 합 **50,000** — 순서가 총액까지 바꾼다 | 처리 속도 ↑(대기 없음) vs 처리 순서 독립성 ↓ | 같은 고객이 담당자의 작업 순서에 따라 다른 총액을 받으면 "공정하다고 느끼게" 할 수 없다. 접수순은 결과를 고객의 행동(접수 시각)에만 의존시킨다. 대가는 같은 고객 선행 건 미판정 시 후속 건 확정 지연이며 이를 화면에 노출한다. 접수순이 고객에게 항상 더 주는 방식은 아니다(R1에선 덜 주거나 같다) |

보조 비교(한 줄): 지위 이전(R3에서 M 30,000) — 최초 판정이 타인의 누적액에 종속돼 예측 불가, 기각. 중복 자동 반려(SKU 일치) — 사례 ② #1110·#1188을 0원으로 만듦, 기각. 알림만 강화하고 적용은 사람에게 — 심사 오류의 원인(선택지)을 남김, 기각.

## 12. 브랜드 방향성 · 톤앤매너 (기획자·디자이너·UX 라이터 전달)

**한 줄**: 심사자가 하루 종일 보는 B2B 백오피스. 신뢰·정확·절제. 숫자와 비교가 주역이고, 화면은 판단의 근거를 먼저 보여준 뒤 행동을 허용한다.

**의미 제약(위반하면 요구사항 실패)**
1. 적용 정책과 비교용 발효 중 정책이 구별돼야 한다 — 적용은 읽기 전용, 현재는 선택지가 아니다.
2. 3축 상태가 서로 다른 축으로 읽혀야 한다 — 한 배지 체계로 섞으면 "유효·0원"을 반려로 읽는다. 색 외 단서 병기(NFR-04).
3. 금액은 산정 근거(기준액 → 한도 조정 → 최종)와 함께 계산 순서대로 읽혀야 한다.
4. 차단은 이유와 해결 경로를 함께 보인다 — 이유 없는 비활성만 금지한다.
5. 비가역 행동(발행·확정)은 되돌릴 수 있는 행동과 구별돼야 한다.

**표현 가설(기획·디자인이 검증·변경 가능)**
- 심사 상세는 근거 → 사실 → 판정 → 산식 → 행동 순서를 기본으로 한다. 단 이미 판단한 건(차단·완료)은 차단 이유·결과가 먼저 올 수 있다.
- 세 비교(적용 vs 현재 / 기존값 vs 변경값 / 중복 후보 A vs B)는 공통 라벨·금액·변경 표현을 공유하되 동일 컴포넌트를 강제하지 않는다 — 적용 vs 현재는 선택지가 아니고, 후보 비교는 판단 대상이다.
- 등폭 숫자, 통화·시각 포맷 일관, 산식 세로 배치, 저채도 배경·높은 텍스트 대비, 장식적 그래디언트·마케팅형 KPI 나열 배제, 한빛마트 브랜드 색은 최소 포인트 — 장시간 사용 전제의 가설.

**톤(UX 라이터)**: 사무적·사실 서술. "~됩니다"보다 "9/15 09:47 접수 · 30,000원 적용"처럼 데이터가 문장이다. 감탄사·권유형 금지. 영향 확인 메시지는 부담이 "줄지 않는다"는 방향으로 쓰고 보증 대상을 한정한다("이번 변경은 이미 접수된 4건에 영향을 주지 않습니다" ≠ "예산에 영향 없음"). 고객 안내 근거는 심사 데이터를 그대로 문장화한다.
