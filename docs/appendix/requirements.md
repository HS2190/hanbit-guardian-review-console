# 부록 · 요구사항과 수용 기준

기능 요구사항과 비기능 요구사항, 그리고 해피 패스 밖의 예외·경계 상태입니다. 수용 기준은 "무엇을 해보면 무엇이 나와야 하는가"로 적었습니다.

## 9. 요구사항

### 9.1 문제 → 지표 → 유저 스토리 → 요구사항 추적

| 문제 | 지표 | 유저 스토리 | FR |
|---|---|---|---|
| 지점이 낮추면 기존 부담도 준다고 오해 / 범위 축소 = 무효로 오해 → 예산 초과·분쟁 | K2·K4 | 박지훈: 발행 전에 기존 접수분과 향후 접수분의 경계를 보고 발행하고 싶다 | FR-01~05 |
| 심사자가 접수 당시 정책을 못 찾아 현재 정책 적용 | K1·K5 | 최민아: 상세 진입 즉시 접수 당시 조건을 보고, 정책을 고를 수 없어야 안심한다 | FR-06~10 |
| SKU만 보고 중복 / 선순위 미확정인데 후속 확정 | K3·K5 | 최민아: 후보를 원인·시정 대상으로 비교하고 원본 상태를 보며 판정하고 싶다 | FR-11~15 |
| 한도 계산 순서가 사람마다 달라 총액이 달라짐 / 0원을 반려로 표시 | K1·K3 | 최민아: 산식이 보이고 잠긴 뒤 흔들리지 않으며, 막힌 이유와 다음 행동을 알고 싶다 | FR-16~21 |
| 분쟁 시 근거를 다시 만듦 / 고객이 변경을 모름 | K2 | 최민아·고객: 판정이 그대로 안내 근거가 되고 고객이 접수 직전 변경을 안다 | FR-22~25 |

### 9.2 기능 요구사항 (FR) — 수용 기준은 검증 행동과 예상 결과

**정책 (F2·F3·F9·F10)**
- FR-01 지점 담당자는 자기 지점 이벤트의 정책 초안을 만들고 수정할 수 있어야 하며, 발행된 버전은 어떤 필드도 수정할 수 없어야 한다. *수용*: 발행 버전에 수정 시도 시 저장 경로가 없고, 변경은 초안 생성으로만 가능.
- FR-02 발행 시 새 버전 번호·발행 시각·발효 시각·발행자가 기록되고, 이전 버전은 접수 건이 참조할 수 있어야 한다. 발행됐지만 발효 전인 버전은 "현재 정책"으로 표시·적용되지 않아야 한다. *수용*: v2 발행 후 v1 참조 제보의 적용 조건이 v1 값 그대로 조회됨. 예약 버전이 있는 동안 큐·상세의 비교 대상은 발효 중 버전.
- FR-03 발행 직전 영향 확인을 건너뛸 수 없어야 하며, 기존값과 변경값을 항목별로 비교할 수 있어야 한다. *수용*: 변경된 항목만 강조되고, **동일 값 발행은 막히며 사유("변경된 항목 없음")가 표시**된다.
- FR-04 영향 확인은 §4.4의 세 값과 "현재 분류 유지 가정"을 보여야 하며, 변경 항목이 범위·한도일 때 미확정 건 중 해당 건수와 "접수 당시 범위·한도로 계속 심사(무효 아님)"를 명시해야 한다. *수용*: 사례 ①에서 60,000(2건) / 30,000(1건) / 105,000(4건, 그중 변경 항목 해당 3건 90,000)이 표시되고 "대기 N건이 변경된다/무효가 된다"류 문구가 없다. 범위 축소 변형에서 "신선식품 3건 계속 심사(무효 아님)"가 표시된다.
- FR-05 발효 예약(Should)은 결정 ⑨를 따른다. *수용*: 두 번째 예약 시도 시 첫 예약 대체 확인 없이 저장되지 않음.

**심사 상세·큐 (F4·F5)**
- FR-06 심사 상세 진입 시 접수 시각과 접수 당시 조건(결함 유형·기준액·한도·범위)을 즉시 식별할 수 있어야 하며, 버전 번호는 보조 정보다. *수용*: 사례 ① #1042에서 "9/15 09:47 · 유통기한 경과 30,000원"이 추가 조작 없이 식별됨.
- FR-07 적용 정책과 발효 중 정책이 다르면 그 차이를 식별할 수 있어야 하되, 적용 정책은 읽기 전용이고 선택·변경 경로가 없어야 한다. *수용*: 상세·큐 어디에도 적용 버전을 바꾸는 컨트롤이 없음(K1).
- FR-08 심사자는 결함 유형 재분류·중복 관계 변경·유효/무효 판정을 할 수 있어야 하고, 재분류·관계 변경 시 사유 없이는 저장되지 않아야 한다. 금액은 접수 정책 테이블에서 자동 재계산되며 직접 입력할 수 없다. *수용*: 재분류 후 기준액이 접수 정책의 해당 유형 값으로 바뀌고 사유가 기록됨. 인정 유형 밖으로 재분류하면 결과 "범위 외".
- FR-09 큐에서 각 건의 처리 상태·보류 사유(보완 대기 / 선행 판정 대기-유효성 / 선행 판정 대기-금액 / 조정 중)·적용 버전≠발효 중 버전 여부를 식별할 수 있어야 하며, 사유별 건수를 상세 진입 없이 확인할 수 있어야 한다.
- FR-10 확정이 막힌 경우 이유와 다음 행동(대상 선행 건으로 이동)이 표시되어야 하며, 이유 없는 비활성 상태만 두지 않는다. 사유가 복수면 모두 표시한다. *수용*: 사례 ③ #1063에서 "같은 고객의 선행 건 #1042 판정 필요"와 이동 경로가 표시.

**중복 판정 (F6)**
- FR-11 같은 지점·이벤트에서 SKU/위치/결함 유형/시각이 겹치는 제보를 후보군으로 볼 수 있어야 하며, SKU 일치만으로 중복이 자동 확정되지 않아야 한다. *수용*: 사례 ② #1110은 후보군에 나타나되 기본값이 "중복"이 아님.
- FR-12 후보 비교는 지점·상품 개체(위치·사진)·결함 유형·접수 시각·증빙·지점 조치 기록을 축으로 대조할 수 있어야 한다. *수용*: 사례 ② 4건에 대해 판정 근거가 축별로 대조 가능하고, #1188 비교에 #1103의 9/17 조치 기록이 보임.
- FR-13 중복 판정 시 원본 지정이 필수이며, 원본의 ID·처리 상태·심사 결과·접수 시각이 표시되어야 한다(원본 고객 개인정보 비노출). *수용*: 원본 없이 "중복" 저장 불가.
- FR-14 후보군에 더 이른 미판정 건이 있으면 최초 유효 확정이 보류되고 "선행 판정 대기(유효성)"로 전환되어야 한다. 선행 건이 무효·만료되면 자동 재검토(심사 중으로 복귀)되며 자동 승인되지 않는다. *수용*: 선행 건 만료 시 후속 건이 "심사 중"으로 돌아오고 결과는 비어 있음.
- FR-15 중복 판정 사유·비교 근거는 고객 안내 근거(TA-2)로 재사용 가능한 형태로 저장되어야 한다. *수용*: #1107 안내 근거에 원본 #1103 접수 시각 9/16 14:02와 사유 "같은 가격표"가 포함.

**지급 확정 (F7·F8)**
- FR-16 지급액 산식은 기준액(접수 정책) → 개인 한도 조정(접수 정책의 한도 − 이벤트 누적 소비) → 최종액 순서로 표시되어야 한다. *수용*: 사례 ③ 분기 A에서 30,000 → −10,000(잔여 20,000) → 20,000. 사례 ② #1188에서 30,000 → 잔여 20,000 → 20,000.
- FR-17 잔여 한도가 음수면 0으로 절삭하고 환수하지 않는다. 유효·0원은 심사 결과 "유효"를 유지하고 지급 상태만 "해당 없음(한도 소진)"이어야 한다. *수용*: R1 케이스에서 B = 0원, 결과 "유효·최초".
- FR-18 같은 고객의 더 이른 제보가 미판정이면 후속 건은 "선행 판정 대기(금액)"로 전환되고 금액 범위(하한~상한)를 보여야 한다. *수용*: 사례 ③ #1063에 "20,000~30,000".
- FR-19 확정 시 금액과 한도 소비가 잠기며, 이후 정책 변경·타 건 판정으로 자동 재계산되지 않아야 한다. *수용*: 확정 후 같은 고객의 다른 건 판정이 바뀌어도 확정액 불변(재심 경로로만 변경).
- FR-20 보완 요청·기한·만료·상품/결함 변경 시 원 건 처리는 결정 ④를 따른다. *수용*: 2회째 보완 요청 컨트롤 없음(§14-5 시스템 귀책 재요청 예외 제외), 만료 시각 = 최초 요청 시각 + 7일이며 추가 제출 후에도 불변, 기한 내 추가 제출 경로 존재, 만료 시 이 건을 선행으로 둔 대기 건이 재검토로 전환(사례 ③ 대안 분기 B: #1042 만료 → #1063 재검토). 기한 전(9/24) 제출 → 기한 후(9/26) 검토 → 충분하면 기존 순위·v1로 심사 계속(자동 종결 없음).
- FR-21 재심에서 정책은 고정되고 사실 판단·중복 관계·산정만 수정 가능해야 한다. 선행 판정 번복 시 결정 ③의 하류 건이 "재심 대상"으로 자동 진입해야 한다(자동 승인 아님, 기존 확정액 유지). 한도 복원은 결정 ⑤를 따른다. *수용*: R4 케이스에서 C가 재심 대상 큐에 나타나고 금액은 20,000 유지. R1 변형에서 A 무효 시 B(유효·0원 완료)가 재심 대상에 포함.

**고객 안내·트랙 A 접점 데이터 (F5·F10)**
- FR-22 심사 완료 시 고객 안내 근거(접수 시각·적용 조건·결과·산식·중복이면 원본 접수 시각·이의 제기 기한)가 심사 데이터에서 자동 구성되어야 한다. *수용*: 사례 ③ 분기 A의 김서연 안내에 30,000 / 한도 50,000 / 기소비 30,000 / 지급 20,000이 포함.
- FR-23 접수 직전 재확인(TA-1)을 위해 "고객이 마지막으로 동의한 버전"과 "제출 시점 발효 중 버전"을 비교해 차이 항목을 산출하는 데이터가 정의되어야 한다. *수용*: 10:20 시작·10:25 제출 케이스에서 v1·v2 차이 항목 1개(유통기한 경과 30,000 → 10,000) 산출.
- FR-24 changelog 데이터는 버전별 발효 시각·변경 항목(이전 → 이후)·발행자를 제공해야 한다(탐색 UI는 Should). *수용*: v2 항목 = 9/15 10:23 · 유통기한 경과 30,000 → 10,000 · 박지훈.
- FR-25 심사 완료·유효 건에 지점 조치 완료(시각·메모)가 기록될 수 있어야 한다(입력 기능 Nice, 데이터 In). *수용*: #1103에 "9/17 가격표 교체 완료"가 있고 #1188 판정 근거에서 조회됨.

### 9.3 비기능 요구사항 (NFR)
- NFR-01 모든 판정·수정·발행은 행위자·시각·이전값·이후값·사유가 기록되어야 한다(탐색 UI는 범위 밖).
- NFR-02 권한: 지점 담당자는 자기 지점 정책만 편집·발행하고 제보는 읽기 전용, 타 지점에 접근할 수 없다. 본사 심사자는 전 지점 제보를 심사·확정하고 정책은 읽기 전용이다. 조정(환수·추가 지급·한도 복원)은 본사 운영팀 별도 권한 (가설).
- NFR-03 동시성: 같은 초안을 두 사람이 편집하면 나중 저장이 이전 저장을 덮어쓰지 않고 충돌을 알려야 한다. 같은 제보를 두 심사자가 열면 확정은 한 명만 가능해야 한다.
- NFR-04 접근성: 3축 상태는 색만으로 구분하지 않고 라벨·아이콘을 병기하며, 텍스트 대비는 WCAG AA(4.5:1) 이상. 발행·확정 등 비가역 행동은 키보드로 조작 가능해야 한다.
- NFR-05 지정 viewport(1440×900)에서 심사 상세의 접수 근거·산정 상태·차단 이유의 **요약**을 스크롤 없이 확인할 수 있어야 한다. 상세는 스크롤을 허용한다(가설 — 기획에서 검증).

### 9.4 예외·경계 상태 (해피 패스 밖)

| 상황 | 요구 |
|---|---|
| 발효 중 버전이 없는 이벤트 | 접수 개시 불가. "발효 버전 없음"과 초안 발행 유도 |
| 영향 확인 대상 접수분 0건 | 세 값 모두 0·0건으로 표시(빈 상태여도 구조 유지), 향후 접수분 조건만 강조 |
| **발행·확정 실패**(저장 오류·충돌) | 초안은 유지되고 부분 발행은 없다. 확정 실패 시 금액·한도는 잠기지 않는다. 실패 사유와 재시도 경로 표시 |
| 빈 상태 — 큐 0건 / 조건 결과 0건 / 중복 후보 0건 | 사유별로 구분(대기 건 없음 vs 조건 불일치 vs 후보 없음). 최초 유효 판정은 후보 없이 진행 가능 |
| 증빙 사진 로드 실패·손상 | 유효성 판정 보류, 보완 요청 경로 제공(횟수 1회 소비 여부 (가설)) |
| 발효 시각 = 접수 시각 / 접수 시각 동일 밀리초 / 동의 후 수신 전 다른 버전 발효 | §4.2 |
| 이벤트 종료 후 대기 건 | 접수 정책으로 끝까지 심사. 종료는 신규 접수만 차단 |
| 지점 담당자가 타 지점 제보 URL 직접 접근 / 본사 심사자가 정책 편집 시도 | 권한 없음 안내·데이터 비노출 / 읽기 전용 |
| 확정 후 선행 건 재심 번복 / 보완 응답이 상품·결함을 바꿈 / 조정 중 고객의 신규 접수 | 결정 ③ / 결정 ④ / 결정 ⑤ |
| 예약 발효 시각 도래 시 초안 편집 중 | 예약 버전 발효, 편집 중 초안은 별개로 유지 |
