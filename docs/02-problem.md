# 02 · 문제와 근거

## 겉으로 드러난 문제

제출 당시 3만 원이던 리워드가 심사 대기 중에 1만 원으로 내려가면, 고객은 제출할 때 본 것과 다른 돈을 받습니다. 심사자는 이 제보가 어느 시점 기준인지 확인할 방법이 마땅치 않아 지금 값으로 판단합니다. 제출 당시 대상이던 카테고리가 범위에서 빠지면 무효 처리됩니다.

## 제가 정의한 문제

> **정책 변경 시 기존 제보에 무엇을 적용할지에 대한 기준과, 심사자가 그 기준을 확인하고 집행하는 수단이 일치하지 않는다.**

데이터에 이력이 없어서 생기는 문제로 단정하지 않았습니다. 이력이 있어도 심사하는 순간의 화면에서 찾을 수 없으면 같은 오류가 납니다. 반대로 화면만 고치고 기준이 없으면 심사자마다 다르게 판단합니다. **기준과 수단은 함께 있어야 합니다.**

그래서 한 제보를 접수 당시 정책으로 심사할지 현재 정책으로 심사할지가 정해져 있지 않습니다. 기준이 둘이면 누가 성실하게 일해도 결과가 갈립니다.

## 문제 상황에 없던 것 세 가지

과제가 준 상황에는 없지만 실제로 운영하면 반드시 부딪히는 문제입니다. 이 셋이 설계의 난이도를 결정했습니다.

| | 숨은 문제 | 왜 문제인가 |
|---|---|---|
| **H1** | 같은 상품 코드가 같은 사건은 아니다 | 같은 진열대의 파손품 두 개, 한 가격표 오류를 찍은 여러 고객, 조치한 뒤 다음 주에 재발한 오류. 무엇을 같은 사건으로 묶느냐가 지급 대상 수를 바꾼다. 상품 코드가 같다고 자동으로 중복 처리하면 유효한 제보자를 0원으로 만든다 |
| **H2** | 선행 건이 미판정이거나 무효가 되면 | 더 이른 제보가 보완 대기 중이면 뒤 제보의 최초 지위를 확정할 수 없다. 선행이 무효가 되면 뒤 건은 자동 승인이 아니라 독립적인 유효성 평가가 필요하다 |
| **H3** | 1인 한도를 여러 건이 공유한다 | 서로 다른 버전으로 접수된 제보들이 하나의 누적액을 나눠 쓴다. 배정 순서 규칙이 없으면 담당자의 처리 순서가 고객의 총액을 바꾼다 |

H3는 숫자로 확인했습니다. 한도가 5만 원에서 3만 원으로 내려간 상황에서 같은 고객의 두 건을 A → B 순으로 처리하면 합이 3만 원, B → A 순으로 처리하면 5만 원이 됩니다. 처리 순서가 총액을 바꿉니다.

## 근거로 삼은 공개 사례 다섯

같은 구조를 이미 겪은 산업이 있습니다. 취약점 신고 포상 플랫폼입니다. 리포트가 제보이고, 포상 테이블이 정책이고, 분류 심사가 심사입니다. 아래는 공개된 운영 문서와 공지에서 가져온 것입니다.

| | 사례 | 출처 |
|---|---|---|
| **E1** | 포상 테이블이 바뀌면 그 이전 제출분은 이전 테이블로 지급하라 | HackerOne 운영 가이드 |
| **E2** | 하향 개편 시 발효일 이전 제출분과 백로그는 이전 구조로 존중한다 | GitHub 2026년 7월 개편 공지 |
| **E3** | 가격 조건 변경은 값을 고치지 않고 새 객체를 만든다. 기존 구독은 옛 값을 유지한다 | Stripe 개발 문서 |
| **E4** | 중복은 같은 조치로 해소되는 것을 말한다. 비슷한 것과 같은 것은 다르다 | Bugcrowd · HackerOne |
| **E5** | 예산 사정의 하향이 이미 처리된 건에 닿으면 분쟁이 된다 | 2026년 5월 보도와 플랫폼 공지 |

E1과 E2와 E3이 같은 말을 합니다. **약속은 제출 시점의 것으로 지킨다.** 다만 이들은 관행이고, 제가 한 것은 그 관행을 심사 화면 위에서 집행 가능한 규칙으로 바꾼 것입니다. 실제 플랫폼은 사유가 있으면 담당자가 금액을 바꿀 수 있게 열어 둡니다. 저는 그 선택지를 닫았습니다. 이유는 다음 문서에 있습니다.

E5는 반대 방향의 증거입니다. 이미 끝난 일에 새 기준을 적용하면 무슨 일이 벌어지는지를 보여줍니다.
